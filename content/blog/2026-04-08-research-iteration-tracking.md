## 문제

연구 iteration에서 같은 작업이 반복됨. 6개월 전 결론이 떠오르지 않아서 같은 결론에 다시 도착. iteration 횟수가 늘수록 비용 quadratic.

## git branch는 답이 아니다

분기 구조만 보면 branch가 자연스러워 보이지만 두 가지가 안 맞음.

- **frozen evidence**: reviewer가 "Fig 3 어떤 코드/입력으로 만들었나" 물으면 답해야 함. git main head는 mutable이고 history는 rewrite 가능. 결국 tag를 찍어야 하는데 그러면 branch 모델이 아니라 tag 모델임.
- **산출물의 영속성**: iteration의 가치는 코드 변경이 아니라 결과 파일 (figure, processed data). git merge가 다루는 건 코드 변경. 결과 파일까지 다루려면 LFS/DVC 필요 → 인프라 비용 큼.

## 디렉토리 스냅샷도 부족하다

대안: `iterations/017/`, `iterations/018/`, ... 각 iter가 자신의 PLAN/TASKS/code/data를 한 폴더에 박제.

- 코드 중복 발생하지만 reproducibility 구조적 보장
- 횡단 비교 용이 (`diff iter17/T05 iter18/T01`)
- 학생도 cp -r 한 줄로 따라할 수 있음

여기까지는 OK. 그러나 이것만으로 까먹기는 안 풀림. 19개 iteration 디렉토리가 있어도 6개월 후 안 뒤짐. 검색이 안 되서가 아니라 **압축된 altitude의 요약이 없어서**.

## 진짜 문제: research memory

까먹기는 분기 구조 표현 문제가 아니라 research memory 문제. 과거 작업이 다음 셋을 만족해야 안 반복함.

1. **Searchable** — 키워드로 즉시 찾아짐
2. **압축된 altitude** — 결론이 1-2줄 어딘가에 박제. PLAN.md 80줄 다시 읽어야 알면 안 봄.
3. **Cross-referenceable** — 새 iter가 과거를 명시적 link

## entity 셋의 분리

iteration이 primary entity가 아니라, 그 안의 셋이 primary.

| Entity | 수명 | 재사용 | 예시 |
|---|---|---|---|
| **Idea** (가설/질문) | 길다 (수년) | 여러 iter에서 test/refine | "image potential의 dielectric knob 영향" |
| **Method** (방법) | 중간 | 여러 idea를 시험 | "Silkin closed-form splice w/ closed-form A,λ" |
| **Result** (결과) | 영구 | 인용, 비교됨 | "iter17 T05: NG=37 수렴, ΔE<0.1meV" |

iteration = 셋의 조립. "전에 해본 적 있나" → `grep -r "..." ideas/` 로 끝남.

## MVP

idea/method/result 분리는 처음부터 하면 over-design. 시작은 PLAN.md frontmatter 표준화 + 인덱스 generator.

```yaml
---
iter: 017
parent: 015                    # 016이 dead-end였으면 015
status: promoted               # active | promoted | dead_end | superseded
title: "Coupled-1D pipeline formalization"
hypothesis: "Silkin splice + closed-form A,λ로 reproduce, NG=37 수렴"
key_findings:                  # 1-2줄 결론. 미래의 나에게 보내는 메시지.
  - "NG=37 basis에서 ΔE < 0.1 meV 수렴 (T05)"
  - "Taper 영향 +0.42 meV, FWHM 0 (T04)"
  - "zim sensitivity는 T03에서 충분"
related_iters: [012, 013]      # cross-reference
---
```

generator (50줄 미만 Python):

- 모든 PLAN.md frontmatter 읽기
- parent chain → mermaid 트리
- 모든 iter 한 줄 요약 → 테이블
- 결과 → `iterations/INDEX.md`

INDEX 한 파일을 새 iter 시작 시 무조건 첫 번째로 읽음. 원리: *항상 컨텍스트에 있는 압축된 인덱스*. ~/.ai/memory/MEMORY.md와 같은 패턴.

## ritual

도구만으로는 안 됨. 두 ritual을 박는다.

**iter 시작:**

1. `iterations/INDEX.md` 읽기
2. hypothesis 키워드로 grep
3. 비슷한 게 있으면 `related_iters`에 명시

**iter 종료:**

1. `key_findings` 채우기
2. 새 가설/방법은 별도 노트로 추출
3. INDEX 갱신 후 commit

프로젝트 `CLAUDE.md`에 박으면 Claude Code가 매번 강제 실행. ritual이 없으면 도구도 안 굴러감.

## LFS 없이 큰 파일

raw data, run dump, 큰 plot은 `.gitignore`. 결과 메타데이터만 텍스트로 박제.

```yaml
---
iter: 017
task: T05-basis-convergence
figure: iterations/017/T05/figs/convergence.png
data_path: ~/scratch/128-gd2c-trap/iter017/T05/runs/
---
**Generated by**: `python iterations/017/code/bands.py --NG-shells 0..5 --basis-scan`
**Reproduction**: `make -C iterations/017/T05 convergence`
**Conclusion**: NG=37에서 ΔE_GS < 0.1 meV 수렴.
```

원본 잃어도 reproduction 명령으로 재생성 가능. 박제할 것은 결론과 재생성 레시피지 raw bytes가 아님.

## Phase 2 — entity 분리

MVP 한두 달 써보고 부족하면 idea/method/result를 별도 파일로 분리.

```
iterations/
  ideas/
    I001-image-potential-dielectric.md
    I007-zim-cutoff-effect.md
  methods/
    M001-silkin-closed-form.md
  results/
    R017-T05-NG37-convergence.md
  018/
    PLAN.md   # frontmatter: ideas: [I003, I007]
```

각 노트: frontmatter + 본문 1-2 단락 + wikilink. Obsidian-style. idea 진화를 별도 그래프로 추적 가능.

처음부터 풀 시스템을 구축하면 시스템 자체가 일이 됨. MVP가 부족하다고 *판단된 후* Phase 2.

## 결론

- iteration 까먹기 = 분기 구조 표현 문제 아님
- = 한 줄 요약과 ritual의 부재 문제
- 해결: frontmatter `key_findings` + INDEX 한 파일 + 시작/종료 ritual
- entity 분리는 그 다음
