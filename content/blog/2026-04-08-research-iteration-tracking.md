연구 프로젝트를 한참 진행하다 보면 자꾸 같은 걸 반복한다. "이 sensitivity test 전에 한 번 해본 것 같은데"가 생기면 옛날 디렉토리를 뒤지기 시작한다. 보통은 못 찾고, 또 한다. 6개월 전의 내가 무슨 결론을 냈는지 기억이 안 나서 같은 결론에 또 도착한다. iteration 횟수가 늘수록 이 비용은 quadratic하게 커진다.

이 문제를 git branch로 풀려고 했다가 한참 뒤에 그게 답이 아니라는 걸 깨달았다. 정리해본다.

## git branch는 답이 아니다

연구 iteration이 분기 구조를 갖는다는 점만 보면 git branch가 자연스러워 보인다. main = "현재까지의 정설", branch = "탐색 중인 가설", merge = "promotion". 깔끔하다. 그런데 두 가지가 안 맞는다.

**1. frozen evidence 보존이 안 된다.** 논문 reviewer가 "Fig 3는 정확히 어떤 코드와 어떤 LOCPOT으로 만들었나"고 물으면 답할 수 있어야 한다. git main의 head는 움직이고 history는 rewrite 가능하다. 그래서 "그때 그 코드"를 박제하려면 결국 tag를 찍어야 하는데, 그러면 branch 모델이 아니라 tag 모델이다.

**2. 산출물의 영속성 문제.** iteration이 만들어내는 진짜 가치는 코드 변경이 아니라 결과 파일(figure, processed data)이다. git branch의 merge가 다루는 건 코드 변경이지 결과 파일이 아니다. 결과 파일까지 merge하려면 LFS나 DVC가 필요해지고, 갑자기 인프라가 무거워진다.

대신 디렉토리 스냅샷 패턴(`iterations/017/`, `iterations/018/`, ...)을 쓸 수 있고, 실제로 내 프로젝트 중 하나는 이렇게 굴러가고 있다. 각 iteration이 자신의 PLAN, TASKS, code, data를 한 폴더에 박제해서 들고 있는 방식이다. 코드가 중복되지만 reproducibility가 구조적으로 보장되고 횡단 비교가 쉽다.

그런데 이것만으로는 "까먹기" 문제가 안 풀린다. 19개 iteration 디렉토리가 있어도 6개월 후에 그 안을 뒤지지 않는다. 안 뒤지는 이유는 검색이 안 돼서가 아니라, **압축된 altitude의 요약이 없기 때문**이다.

## 진짜 문제: 세 entity의 분리

까먹기 문제는 branch/디렉토리 구조 문제가 아니라 **research memory** 문제다. 과거 작업이 다음 셋을 만족해야 다시 안 반복한다.

1. **Searchable** — 키워드로 즉시 찾아짐
2. **압축된 altitude** — 결론이 1-2줄로 어딘가 적혀 있어야 함. PLAN.md 80줄을 다시 읽어야 알면 안 봄.
3. **Cross-referenceable** — 새 iteration이 과거를 명시적으로 link할 수 있어야 함

그리고 더 중요한 관점 전환이 있다. 지금까지 iteration을 primary entity로 다뤘는데, 사실 primary는 그 안의 세 가지다.

| Entity | 수명 | 재사용 | 예시 |
|---|---|---|---|
| **Idea** (가설/질문) | 길다 (수년) | 여러 iteration에서 test/refine | "image potential의 dielectric knob이 surface state에 큰 영향?" |
| **Method** (방법) | 중간 | 여러 idea를 시험하는 데 재사용 | "Silkin closed-form splice with closed-form A, λ matching" |
| **Result** (결과) | 영구 | 인용, 비교됨 | "iter17 T05: NG=37 basis로 수렴, ΔE < 0.1 meV" |

iteration은 이 셋을 묶어서 한 사이클 돌린 것이고, primary entity가 아니라 이들의 *조립*이다. 이렇게 보면 "이 sensitivity test 전에 해봤나"는 `grep -r "sensitivity" ideas/` 한 줄로 끝난다.

## MVP

idea/method/result를 처음부터 분리하면 over-design이다. 가장 작은 시작은 `PLAN.md` frontmatter 표준화 + 한 줄 요약 인덱스다.

```yaml
---
iter: 017
parent: 015                    # 016이 dead-end였으면 이렇게
status: promoted               # active | promoted | dead_end | superseded
title: "Coupled-1D pipeline formalization"
hypothesis: "Silkin splice + closed-form A,λ로 reproduce, NG=37 수렴"
key_findings:                  # 미래의 나에게 보내는 메시지
  - "NG=37 basis에서 ΔE < 0.1 meV 수렴 (T05)"
  - "Taper 유무 차이 +0.42 meV, FWHM 영향 0 (T04)"
  - "zim sensitivity는 T03에서 충분 — 다음 iter에서 재실행 불필요"
related_iters: [012, 013]      # 명시적 cross-reference
---
```

이 frontmatter 위에 generator 하나만 있으면 된다. 50줄 미만의 Python 스크립트가 모든 PLAN.md를 읽어서 두 가지를 만든다.

- **Tree view** (mermaid): parent chain으로 분기 구조 시각화
- **Index table**: 모든 iteration의 한 줄 요약

결과물은 `iterations/INDEX.md`에 박힌다. 이 한 파일이 항상 첫 번째로 읽혀야 한다. 새 iteration을 시작하기 전에 무조건 INDEX를 읽으면 까먹기의 90%가 사라진다. 원리는 단순하다 — *항상 컨텍스트에 있는 압축된 인덱스*.

## ritual이 시스템보다 중요하다

도구만으로는 안 된다. 두 가지 ritual이 박혀야 한다.

**Iteration 시작 의식:**
1. `iterations/INDEX.md` 무조건 읽기
2. 새 PLAN의 hypothesis 키워드로 grep 한번 (`ideas/`, 과거 PLAN의 `key_findings`)
3. 비슷한 게 있으면 `related_iters:`에 명시

**Iteration 종료 의식:**
1. `key_findings:` 채우기 (1-2줄, 미래의 나에게 보내는 메시지)
2. 새로 발견한 가설/방법은 별도 노트로 추출
3. INDEX 갱신 후 commit

이 두 ritual을 프로젝트 `CLAUDE.md`에 박으면 Claude Code가 매번 강제 실행한다. 혼자 작업할 때도 Claude가 reminder 역할을 한다. 시스템보다 ritual이 더 중요한 이유는, 결국 까먹기는 도구가 아니라 *일을 시작/끝낼 때 무엇을 하느냐*의 문제이기 때문이다.

## LFS 없이 큰 파일 다루기

raw data, run dump, 큰 plot 같은 건 그냥 `.gitignore`에 넣는다. 대신 결과의 메타데이터는 텍스트로 박제한다.

```yaml
---
iter: 017
task: T05-basis-convergence
figure: iterations/017/T05/figs/convergence.png
data_path: ~/scratch/128-gd2c-trap/iter017/T05/runs/
---
**Generated by**: `python iterations/017/code/bands.py --NG-shells 0..5 --basis-scan`
**Reproduction**: `make -C iterations/017/T05 convergence`
**Conclusion**: NG=37 (5 shells)에서 ΔE_GS < 0.1 meV 수렴.
```

원본 데이터를 잃어도 reproduction 명령으로 재생성 가능하다. 사실상 "LFS의 가난한 자 버전"인데, 연구 목적으로는 충분하다 — 진짜 잃어선 안 되는 건 *결론*과 *재생성 레시피*지 raw bytes가 아니다.

## Phase 2 — entity 분리

MVP를 한두 달 써보고 부족하면 idea/method/result를 별도 파일로 뺀다.

```
iterations/
  ideas/
    I001-image-potential-dielectric.md
    I007-zim-cutoff-effect.md
  methods/
    M001-silkin-closed-form.md
  results/
    R017-T05-NG37-convergence.md
  018/
    PLAN.md   # frontmatter: ideas: [I003, I007]
```

각 노트는 frontmatter + 본문 1-2 단락 + wikilink. Obsidian-style이다. 이 단계가 되면 진짜로 idea가 어떻게 진화했는지 별도의 그래프로 추적할 수 있다.

다만 이건 MVP가 부족하다고 *판단된 후*에 한다. 처음부터 풀 시스템을 만들면 시스템 자체가 일이 되고, 정작 연구는 안 된다. 도구를 만드는 게 핵심 작업처럼 느껴지기 시작하는 순간이 가장 위험한 순간이다.

---

이 글의 결론은 사실 단순하다. 연구 iteration의 까먹기 문제는 *분기 구조 표현 문제*가 아니라 *한 줄 요약과 ritual의 부재 문제*다. 해결도 단순한 데서 시작한다 — frontmatter에 `key_findings` 필드 하나, 모든 iter의 한 줄 요약을 모은 INDEX 한 파일, 시작/종료 시 그걸 읽는 ritual. 더 정교한 entity 분리는 그 다음이다.

자기 자신의 과거 작업이 검색되지 않는 연구자는 같은 길을 두 번 걷는다. 매번 처음 걷는 것처럼.
