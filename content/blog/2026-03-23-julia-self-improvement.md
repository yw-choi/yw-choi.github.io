[Julia](/blog/2026-03-21-julia-design/)는 Slack과 Gmail로 지시를 받아 일하는 AI 에이전트다. 그런데 지시를 받아서만 일하면 시스템이 개선되지 않는다. 에러가 나도 사람이 발견할 때까지 방치되고, 더 나은 방법이 있어도 알아서 찾아보지 않는다. Julia에는 이 문제를 해결하는 세 가지 자동 피드백 루프가 있다.

## 1. 스스로 개선 아이디어를 찾는다

매일 cron으로 `self_improve.py`가 실행된다. Claude Code를 호출해서 인터넷을 검색하고, Julia를 개선할 아이디어를 찾는다.

검색 영역은 다섯 가지다:

- Claude Code 신기능과 MCP 서버
- AI 에이전트 자동화 패턴
- 개인 AI 워크플로우 개선 사례
- 연구 생산성 도구
- Obsidian + AI 통합

각 아이디어는 세 축(실용성, 영향력, 구현 노력)으로 1-5점 채점된다. 합산 12점 이상인 것만 남기고, 상위 3개를 `self-improve` 라벨이 달린 GitHub issue로 자동 생성한다. 요약 리포트는 Slack DM으로 온다.

결과적으로 매일 아침 Slack에 "이런 걸 적용하면 좋겠다"는 제안이 올라온다. 사람은 issue를 훑어보고 할지 말지만 판단하면 된다.

## 2. 에러를 스스로 진단한다

Watchdog이라는 별도 프로세스가 세 개의 로그 파일(`julia.log`, `claude.log`, `activity.log`)을 실시간으로 감시한다. ERROR 레벨 로그나 `is_error: true` 기록이 발견되면:

1. 10분 윈도우로 중복을 제거한다 (같은 request_id나 메시지 해시)
2. Claude Code를 호출해서 원인, 영향, 수정 방법을 분석한다
3. `bug`, `auto-watchdog` 라벨이 달린 GitHub issue를 생성한다
4. Slack으로 알림을 보낸다

에러 컨텍스트(전후 로그, 관련 활동 기록)가 issue에 포함되기 때문에, issue만 읽으면 바로 수정에 들어갈 수 있다. 사람이 로그를 직접 뒤질 필요가 없다.

## 3. 기억의 정합성을 검증한다

Julia는 Claude Code의 memory 시스템을 사용한다. memory 파일에는 프로젝트 상태, 일정, 사람-프로젝트 관계 같은 정보가 기록되어 있다. 문제는 현실이 바뀌어도 memory가 자동으로 업데이트되지 않는다는 점이다.

`memory_audit.py`가 이걸 잡는다:

- 연구 프로젝트 memory와 GitHub repo의 archive 상태를 대조한다
- 지난 날짜의 이벤트가 아직 "upcoming"으로 표시되어 있으면 감지한다
- 행정 업무 상태와 실제 repo 상태를 비교한다
- `MEMORY.md` 인덱스와 실제 파일 목록을 대조한다

불일치가 발견되면 Slack으로 보고한다. memory가 현실과 어긋나면 Julia의 판단도 어긋나기 때문에, 이 검증은 시스템 신뢰성에 직접 영향을 준다.

## 세 루프의 관계

```
self_improve.py (공격) → "이런 기능을 추가하면 좋겠다"
watchdog.py     (방어) → "이 에러가 발생했고, 원인은 이것이다"
memory_audit.py (정합) → "이 기억이 현실과 다르다"
```

공격(새 기능 제안), 방어(에러 감지와 진단), 정합(지식 검증)이 각각 독립적으로 돌면서 시스템을 개선한다. 세 루프 모두 GitHub issue나 Slack 메시지로 결과를 남기기 때문에, 사람의 역할은 실행이 아니라 판단이다.

---

이 구조의 핵심은 AI 에이전트가 단순히 지시를 수행하는 것을 넘어, 자기 자신을 모니터링하고 개선 방향을 제안한다는 점이다. 물론 실제 코드 변경은 사람이 검토하고 승인한다. 하지만 "무엇을 고쳐야 하는가"를 찾는 작업 자체를 자동화한 것만으로도, 시스템 유지보수의 인지 부하가 크게 줄어든다.
